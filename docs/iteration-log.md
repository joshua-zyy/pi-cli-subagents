# 插件迭代记录

本记录用于决定下一步优化方向：保留问题、方法、分支及验证结论，既记成功，也记无效、排除和未验证的尝试。它不是发版说明，也不是外部任务的正确性背书。

## 维护约定

1. 每个问题使用稳定编号；一次方法一行。开始前写清观察证据、预期改善和失败条件，不为凑迭代而改代码。
2. 方法必须关联分支与提交；未实施写“未实施”，未提交写“未提交”。分支可删除，提交 hash、结论与失败原因保留，不重写失败历史。
3. 分开记录**方法效果**和**交付门槛**：反例转绿不等于全量通过，全量偶然绿不等于根因修复；评审通过不能覆盖失败断言。功能有效但仍未过合并门槛，不记为“已解决”。
4. 问题状态使用“验证中”“已验证并合并”“无效”“已排除（未实施）”或“证据不足”。无效/排除项须写何种新证据才值得重试；未验证、无样本与产物不可用不算通过。
5. 每轮检查与每次方法结论变化后更新；每 3 轮真实任务集中汇报。先与 oracle 讨论，再独立分支实施、测试、评审、复测；有效且过门后才合并本地 main。推送与发布不在自动流程内。

只审查插件的工具可用性、信息完整性、通知、状态、审批与恢复。模型判断、上游接口和外部任务环境单独归类；不因任务失败就归咎插件或代为修补。收集结果前不得预填“已解决”。

### I-002：先确认原 worker 退出，再构造终态 stale lock

**观察与根因**：`manager-recovery.test.mjs` 的 stale-lock 用例在 released 后立刻伪造 owner.lock。释放原生 CLI 和删除 owner.lock 时，worker 的 event loop 仍可存活；伪造锁使 view 变为 unreachable，close 可能先请求已关闭的端口，安全拒绝却报 ECONNREFUSED，未到达测试所期望的 lock/owner 诊断。该测试前置条件比生产 close 契约更强。

### I-003：过期通知候选不重复实施

旧记录称最终通知总带 Read result 提示。核对当前 [notifier](../src/notifier.ts)、已有 `05ce821` 与 `fa26d1a` 后，提示已限于被截断的最终报告，遗漏区定位与 12000 查询上限也已有实现。

方法：先对照当前源码、构建和历史提交，再判断旧问题是否仍在；未另开实现分支。结论为**已排除（未实施）**，不是本批修复。仅在当前版本捕获到未截断通知仍诱导重复查询，或补读不能覆盖遗漏区的新反例时重开。

### I-004：一次 Claude stop 超时不作根因修复声明

I-001 最终 689 集的一次运行中，`claude-adapter.test.mjs` 的 “Claude bounds stop even when the native interrupt never acknowledges” 15,000ms 超时，记录耗时 18,210ms，附近有 taskkill exit 1。原 main 与分支整文件各 26/26；后续 test-only 全量 687/687。没有单独修复分支，也没有扩大超时、删断言或修改 adapter。

结论为**证据不足**。后续绿只说明该次未复现，不证明环境归因或已修复。若再次发生，先固定原测试进程身份并区分 native interrupt、强制回收和 cleanup 阶段，再讨论方案。
