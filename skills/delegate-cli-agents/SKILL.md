# Delegate CLI agents

1. **Choose the task boundary.** Delegate independent, concrete work that can be verified. Run `list_agents` to see roles and existing instances. The first release supports Pi CLI subagents only. Avoid spawning more agents than needed.
2. **Brief the agent.** Use `spawn_agent` with `worker` for implementation or `reviewer` for independent assessment. State the goal, authorized files, expected output and verification. An agent shares the chosen `cwd`; a separate conversation is *not* a separate filesystem. Avoid concurrent writes to shared files.
3. **Keep moving.** Spawning is asynchronous; keep working or inspect other tasks. When a running child needs correction, use `send_input` (`steer` arrives after the current tool step; `followUp` waits for the current run). Do not assume either interrupts an in-flight tool. `list_agents` shows status; `list_pending_permissions` shows unresolved child interactions.
4. **Close the loop.** Completion reports arrive in the original parent session. Read errors rather than interpreting empty text as success. For implement → review → fix, start a distinct reviewer in the implementer's directory, evaluate the review findings, then `send_input` to the **same implementer's ID**. A completed child resumes its original Pi session, not a replacement. Review its actual code changes and run appropriate verification yourself before claiming completion.
5. **Handle interruptions deliberately.** `close_agent` stops active work but keeps its session for later continuation; never use it merely because a task finished. On a pending interaction, inspect the full request and the user's original authorization. Use `respond_to_permission` for a single in-scope decision (including explicit denial); supply a concrete reason. If the request exceeds the task scope or is ambiguous, leave it waiting and ask the user to decide via `/agent-reply <agentId> <questionId>` or the TUI. Never treat an approval as blanket permission or bypass the safety extension. If an instance is unreachable, inspect its logs and state instead of spawning a duplicate on the same session. Humans have their own surface in a TUI: a status area above the editor, and `/agents` to inspect results and errors (`v` opens a live conversation with tool inputs and outputs), send instructions, resume an instance's original session, answer a pending request, or stop an instance after confirmation.

The parent must have a persistent Pi session. When the parent exits, an already running subagent can continue and its report is saved. On returning to the **original parent session**, pending reports are delivered; an unrelated session cannot claim them.
